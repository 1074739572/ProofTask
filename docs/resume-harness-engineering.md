## STAR 拆解

### S — 背景（Situation）

自研 Agent Harness（`improved_harness`，基于教学项目 s20 单文件拆包改进的类 Claude Code 框架，
含 agent loop / 工具系统 / 权限 / 会话 / MCP / TUI 双入口），面临三个真实问题：

1. **可靠性无法度量**：只有「基础设施回归测试」，无法回答「同一个模型、不同 harness 配置下，执行可靠性差多少」。
2. **真实缺陷反复踩坑**：bash 命令在 Windows 下挂起、TUI 切换项目后旧规则泄漏、权限被意外绕过——每次都要人工排查。
3. **评测本身不可见**：一次 30-run 评测跑 1 小时，输出全缓冲，中途「看起来没结果」，且单次观测方差极大误导结论。

### T — 任务（Task）

建立一套**可量化、可回归、可对比**的评测与改进闭环，回答：

- harness 改动到底是变好还是变坏？（同一模型、同一任务、不同配置）
- 每个缺陷是否被真正修复？（红→绿可复现）
- 成本是多少？（token / 时间 / 工具调用）

### A — 行动（Action）

**1. 建立 H 系列任务评测（真 LLM，能力层）**
- 7 个受控任务（H001-H007）：单文件修复、跨模块、过度扩展陷阱、跨会话、提前完成陷阱、模糊需求、多文件重构
- 每个任务带独立 oracle（隐藏检查脚本），agent 不可见；「自报完成」与「实际通过」分开记录
- 5 任务 × 2 配置 × 3 次 = 30 次正式运行，统计 token / 时间 / 工具调用 / 回合 / 完成率 / 虚假完成率

**2. 建立 M 系列机制评测（零成本，回归层）**
- 7 项确定性断言（M001-M007）：bash 挂起、平台提示注入、子 agent 工具语义、
  HARNESS.md 可注入、工作区跟随、/open 重载、权限安全红线
- 全零 LLM token（~0.8s/次），可常驻 CI；每项都对应一个真实缺陷或机制点

**3. 修复真实缺陷（均有红→绿证据）**
- **M001 bash 挂起**：bash 子进程继承 TUI 的 stdin 管道 → python 命令永久等待输入（CPU 0、无输出）。
  修复：`subprocess` 统一 `stdin=DEVNULL`。改进前需手动给每条命令加 `< NUL`，改进后 0.2s 返回。
- **M006 项目规则泄漏**：TUI `/open` 切换工作区后不重载新项目的 HARNESS.md，agent 继续遵守旧项目规则。
  修复：对齐 CLI 路径（清空 history + 重载说明 + 重置 ephemeral 缓存）。
- **M007 权限安全漏洞**：持久化规则里一条 `bash:* allow`（一次误点「always」）导致**所有 bash 命令永久免确认**，
  `rm *: deny`、`sudo *: deny` 等红线全部失效。修复：config deny 优先级高于 saved allow（安全红线不可被用户授权覆盖）+ 清理过宽规则。
- **平台提示注入**：Windows 下 agent 先用 ls/grep 踩坑再换 dir/findstr；在每轮 session context 注入
  「System environment: Windows → cmd.exe」提示，跨平台自动适配。

**4. 修评测框架自身的坑**
- 输出全缓冲 → `-u` + `flush=True`，逐 run 实时可见（解决「跑 1 小时没结果」）
- probe 命令字符串 `json.dumps` 转义引号导致 cmd 解析错 → 改用 `repr()`
- Windows 不能删除「当前 cwd」目录 → 测试 finally 恢复 cwd
- 单次 token 方差极大 → 必须 ≥3 次取均值、按任务拆分统计

**5. 数据驱动的上下文分层设计**
- 全局（Runtime facts + 用户级 handbook）与局部（项目 HARNESS.md）分三层，优先级：
  运行时安全/工具事实 > 当前明确要求 > 项目说明 > 全局默认

### R — 结果（Result）

**量化成果（全部实测）：**

| 指标 | 改进前 | 改进后 | 变化 |
|------|--------|--------|------|
| 回归评测通过率 | 87%（29/33） | **100%（33/33）** | +13pp，0 fail |
| bash 跑 python 命令 | 挂起至超时（>120s）或需手动 `< NUL` | **0.2s 返回** | 单次省 ~120s |
| M 系列机制回归 | 无 | 7 项全过，0 token，~0.8s | 新增 CI 防线 |
| H001 任务 token（structured vs baseline） | 136K | 70K | **-48%**（仓库即规范减少探索） |
| 30 次运行平均 token（structured vs baseline） | 198K | 187K | -5.5%（因任务而异，诚实记录） |
| 评测可见性 | 1 小时无输出 | 逐 run 实时输出 | 可观测 |

**发现并修复的缺陷：3 类真实缺陷（含 1 个安全漏洞）**
- 1 个安全漏洞：权限红线可被 saved allow 绕过（已修复 + 固化 M007）
- 1 个可靠性缺陷：bash 挂起（已修复 + 固化 M001）
- 1 个状态一致性缺陷：/open 规则泄漏（已修复 + 固化 M006）

**方法论沉淀：**
- 红→绿评测工作流：先写复现测试（红）→ 修复 → 同测试通过（绿）→ 固化为回归防线
- 双轨评测：M 系列（0 token 常驻 CI）+ H 系列（真 LLM 按需对比）
- 诚实统计原则：单次观测不可信，≥3 次均值、按任务拆分；结论可被数据推翻
  （曾误判「structured 省 4 倍 token」，30 次全量统计修正为 -5.5%）

## 面试可讲的 2 分钟故事

「我给自研 agent harness 做了一套双轨评测。H 系列用 7 个受控任务 + 隐藏 oracle 测真实能力，

其中 M007 是一个真实安全漏洞：一次『always』授权让所有 bash 命令免确认、连 rm/sudo 红线都失效，
修复后回归通过率从 87% 到 100%。现在每次改 harness 跑一遍 `python -m evals`，几十秒就知道有没有改坏。」

## 备注（诚实边界）

- 「工具调用少了多少 / 时间短了多少」：**没有全局性的「工具调用变少」数据**——structured 配置因
  多读状态文件/多轮验证，工具调用反而 +65%（这是设计开销，不是改进）；真正减少的是
  ① 错误命令重试（平台提示）、② 挂起等待（M001）、③ 探索成本（H001 token -48%）。
  简历表述用「token 减少 / 挂起消除 / 通过率提升」这些有据可查的指标，避免说「工具调用减少」。
- 时间 +31.2% 是 structured 的固定开销，属于「用成本换规范」，面试被追问时可如实说明。
