# ProofTask 设计说明：让机器判定交付

## 一句话

ProofTask 不把“完成”当成模型的一句话，而把它定义为一组可重复检查的机器事实：目标明确、任务有验收标准、测试真实存在并通过、证据已经保存。

核心分工是：

```text
模型负责理解、规划和实现；机器负责验证、记录和裁定能否交付。
```

这不是不信任模型，而是把“提出答案”和“证明答案成立”分开。模型可以很有创造力，最终交付却必须可复现、可审计。

## 我们遇到的长期任务问题

长任务的风险不只是模型会不会写代码，而是任务执行过程中，目标和完成标准会逐渐失真。

| 问题 | 发生了什么 | 结果 |
| --- | --- | --- |
| 上下文腐烂 | 历史对话变长，早期约束被压缩、遗漏或被新内容覆盖 | Agent 继续工作，却逐渐偏离原始目标 |
| 过度完成 | 为了“做得更完整”而修改无关模块、增加未要求的功能 | 变更范围膨胀，风险和审查成本上升 |
| 假完成 | 模型根据自己的操作和最后一句话判断“已经完成” | 看似有进展，真实行为可能没有通过验收 |
| 失败漂移 | 一个 Task 失败后直接进入后续工作 | 后续改动掩盖问题，最终无法定位责任 |
| 重启失忆 | 进程或会话中断后只剩对话片段 | 不清楚当前任务、依赖和上一次验证结果 |

这些问题有一个共同根因：执行过程和交付判定混在了一起，模型既是执行者，又被默认为裁判。

## 设计回应

### 1. 用 Task 固定交付边界

Goal 只描述最终目标；Task 才是一次可执行、可验收的交付单元。每个 Task 持久化保存：

- 行为描述和 Given / When / Then 验收案例；
- 对前置 Task 的依赖；
- 绑定的测试 selector 和验证状态；
- 机器证据、失败原因、尝试次数和可选评估结果。

这样，模型的临时 Todo 不会被误认为用户需求已经完成，也不会因为上下文压缩而丢失交付标准。

### 2. 测试必须真实存在，并且先证明“现在还不行”

测试 selector 只能来自系统实际收集到的 pytest 目录。缺少测试时，专门的 `goal_test_writer` 只为当前 Task 补充聚焦测试。

新测试必须在实现前先失败。基线已经通过、超时或执行出错时，系统暂停 Goal，不绑定这个测试。这个门槛避免把“没有覆盖新行为的测试”伪装成验收标准。

### 3. 把最终确认态交给机器

Task 的状态不是模型返回值的投影，而是验证结果的投影：

```text
模型声明完成       -> 仅作为过程信息
绑定测试 exit_code=0 -> 形成机器证据
严格 clean check     -> 允许完成 Task
最终重跑全部绑定测试 -> 允许完成 Goal
```

`evaluator` 可以检查验收案例、代码差异和证据覆盖情况，但它只能提供建议，不能把失败的机器验证改判为通过。

### 4. 让失败回到当前 Task

执行采用 WIP=1：同一时间只处理一个 Task。验证失败时回到当前 Task，记录错误并继续修复；只有当前 Task 通过并完成，依赖它的 Task 才会解锁。

Goal 完成前还会重新运行所有 Task 的绑定测试，再运行用户指定的全局回归命令，防止后续 Task 的修改破坏先前已经通过的行为。

### 5. 状态和证据可以跨会话恢复

Goal、Task、依赖、验证状态和错误信息都落盘保存。暂停、重启或恢复时，系统读取持久化状态，而不是要求模型从残缺的对话上下文重新猜测进度。

## 谁可以决定什么

| 事项 | 模型 | 机器 / Harness |
| --- | --- | --- |
| 理解需求、拆分 Task | 提议 | 校验结构和依赖是否完整 |
| 编写实现 | 执行 | 限定当前 Task 的工作范围 |
| 选择测试 | 提议 | 只接受 Test Catalog 中真实可收集的 selector |
| 判断测试是否通过 | 不能自判 | 执行命令并检查退出码与证据 |
| 判断 Task 是否完成 | 不能覆盖机器结果 | 强制验证和 clean check |
| 判断 Goal 是否交付 | 可以给出总结 | 重跑所有 Task 测试和全局回归 |

## 这套设计解决什么，不能解决什么

它解决的是过程可靠性：完成标准不会随上下文漂移，测试归属清晰，失败不会被掩盖，重启后可以恢复，最终状态有明确的机器依据。

它不能自动保证测试本身覆盖所有业务语义，也不能替代领域专家对验收案例的设计。因此 ProofTask 把测试质量、验收标准和机器证据同时保留下来，而不是用一个模型分数概括它们。
