# Goal 系统总览

> 当前 Goal v2 的唯一总览。早期 MVP 文档只用于了解历史，不应作为运行规则。

## Goal 在解决什么

Goal 不是让一个模型无限工作到它说“完成”。它把一次较大的需求拆成可验证的
Task，并保存每一步的合同、测试证据、机器结果和失败原因。模型可以提出下一步，
但只有机器验证和状态机可以推进交付。

```text
需求
  -> Discovery（只读探索，形成证据）
  -> 规划合同 + 独立审查
  -> Task 测试准备
  -> 执行前检查
  -> 实现切片 -> 机器验证 -> 修复或交付
  -> 全量回归
```

Discovery 属于规划前阶段。它负责较大范围的仓库探索，输出路径、调用关系、测试
目录和证据清单。执行阶段只能读取当前 Task 的 `read_envelope`、目标源码和绑定测试；
它不应再用大范围搜索来重新理解整个仓库。

## 任务合同

一个 Task 必须包含行为、验收条件、依赖、测试策略和以下范围。范围不是模型的建议，
而是运行时权限边界。

| 字段 | 含义 |
| --- | --- |
| `primary_write` | 已存在、允许直接修改的精确文件 |
| `planned_new` | 已证实父目录下、允许新建的路径 |
| `conditional_write` | 有进一步机器证据后才能加入的已有文件 |
| `read_envelope` | 为理解当前 Task 允许读取的文件或目录 |
| `forbidden` | 无论如何都不能修改的路径 |

Goal 合同还固定目标摘要、约束、假设、验证前提和架构决策。合同一旦开始执行，
后续模型不能扩大产品范围、删验收条件或弱化测试。

## 怎样判断范围

### 过宽

出现以下任一情况，合同应被审查或重规划：

- `primary_write` 写成 `src/`、整个应用入口或不相关的一组目录。
- 一个 Task 同时要求模型决定架构、改多个独立模块、补多层测试，且不能独立验证。
- Task 没有精确文件证据，只是写“按需要修改相关代码”。
- 为了通过测试而允许改配置、密钥、部署或其他不在需求内的文件。

过宽的危害不是“多改一点”，而是 worker 需要自行决定产品边界。此时测试通过也难以
说明改动是正确的，且权限扩大无法审计。

### 过窄

出现以下情况，合同可能过窄：

- 绑定测试直接依赖某个未列入范围的源码文件。
- 已有任务实现了局部函数，但调用链或必要的适配层不在可写范围内。
- `planned_new` 的文件需要被一个已存在的注册/导出文件引用，而该文件没有被列出。
- 执行前检查发现合同中的文件已不存在、计划新建文件已存在，或依赖关系不成立。

过窄不等于“worker 想多改一个文件”。只有测试依赖、确定性的调用链证据或规划前
Discovery 证明该路径必要时，才允许修正范围。

### 合适的范围

合适的 Task 让一个新 worker 不需要猜产品架构：它知道要改哪些文件、为何要改、
如何通过哪组测试证明结果。允许一个 Task 覆盖紧密耦合的实现细节，但不应把两个能
分别验收的交付物硬塞在一起。

## 执行闭环

1. `prepare_execution` 检查依赖、冻结合同、范围重叠、文件存在性和验证前提。
2. worker 仅在允许范围内工作；一次 worker 会话只是一个有边界的切片。
3. 切片到达轮数或 token 边界且确实改变了 Task 代码/证据时，进入 `rollover`，先跑
   机器验证，再决定是否需要下一切片。
4. 绑定测试、独立评估或 clean check 失败，均先写入结构化失败原因，再进入修复规划。
5. Task 全部完成后，重跑所有 Task 的绑定测试和 Goal 级全量回归。

因此“模型做了很多动作”不是进展；可观察的代码/证据变化和机器验证才是进展。

## 失败后怎么选路

| 现象 | 路线 | 含义 |
| --- | --- | --- |
| 实现有方向，测试指出明确缺陷 | `implementation_fix` | 保持合同，带着失败证据继续修复 |
| 验收行为缺少有效测试 | `test_gap` | 只补聚焦测试和绑定，不改产品范围 |
| 测试证明遗漏一个必要源码路径 | `scope_omission` | 只按机器证据修正 Task 范围 |
| 多次无进展、拆分/依赖错误 | `replan` | 重新编译并审查未完成 Task |
| 外部服务、凭据、部署权限不可用 | `blocked` | 保留原因并暂停，不伪造完成 |

`replan` 不等于重新生成测试。它保留已完成 Task，取消旧的未完成 Task 作为审计记录，
然后依据原 Discovery 证据和冻结 Goal 合同生成新的未完成任务图。新图仍需经过独立
规划审查；它不能复用已完成任务名，也不能修改 Goal 合同。

## 何时反复审查或修改

规划阶段允许一次格式/合同修正和一次独立审查后的修正。这是为了修复结构化输出或
明确的合同问题，不是让规划模型无限辩论。

执行阶段不按“失败次数”机械判死刑：大型任务可能需要多次实现切片。但系统会在以下
时机停止沿用同一方向并重新分析：

- 切片没有带来 Task 代码或证据变化；
- 测试持续失败，且修复方向没有新的证据；
- clean check 拒绝交付；
- 执行前检查发现原合同无法落地；
- 修复历史显示当前 Task 边界或依赖本身有问题。

如果修复模型不能给出合法 JSON，系统记录该情况并采用受限的本地回退方向；如果模型
或 provider 不可用、原始 Discovery 清单缺失、或涉及工作区外/敏感权限，Goal 会暂停，
而不是静默扩大权限。

## 页面上应该看到什么

Goal 页面显示的不只是“working”：

- 当前阶段和当前 Task；
- 每个 Task 的可写、计划新建、待证据和禁止路径；
- 执行前检查结果；
- 最近的执行决策：实现切片、验证失败分类、续跑检查点、重规划、阻塞；
- 规划审查结论、绑定测试证据和最终回归结果。

这使人可以区分“模型正在读取/实现/验证”与“状态机是否允许继续”，也能追溯某个
权限、范围或重规划决定来自什么证据。

## 边界

系统会自动处理普通的合同内工作和可验证的修复；以下情况必须暂停并留下原因：

- 需要工作区外、密钥、部署、不可逆操作或未批准的敏感权限；
- Goal 合同仍有未决产品选择；
- 外部运行环境或 provider 不可用；
- 没有原始 Discovery 证据，无法安全重规划。

不要手工编辑 `.project/goal.json` 来跳过阶段。正确入口是 `/goal status` 查看执行记录，
解决外部阻塞后使用 `/goal resume`。
