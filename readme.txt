ProofTask
可验证的自主编码执行器

ProofTask 是一个面向真实代码仓库的 Agent Harness。它把复杂需求拆成
可交付的 Task，并要求每个 Task 都有验收标准、已收集的测试选择器和
机器验证证据。

它的核心观点很简单：

  模型说“完成了”不算完成。
  Todo 全部打勾不算完成。
  只有绑定测试实际通过，Task 才能完成并推进下一步。


为什么是 ProofTask
==================

很多自主循环工具擅长“继续做”，但复杂任务真正的风险在于：模型可能
完成了许多局部操作，却没有证明最终行为正确。ProofTask 把执行单元从
模糊的“功能”收敛为可验证的 Task，让自动化过程可检查、可暂停、可恢复。

ProofTask 的目标不是增加一层漂亮的计划，而是减少“看起来完成、实际没
完成”的结果。


核心能力
========

1. Goal 自动拆解为 Task

   一个复杂 Goal 会被拆成多个独立 Task。每个 Task 有明确行为描述、
   Given/When/Then 验收标准，以及依赖关系。后续 Task 只有在前置 Task
   完成后才会开始。

2. 测试先绑定，不能凭空声明

   系统先用 pytest 收集当前仓库真实存在的测试节点。规划模型只能选择
   这些节点，不能编造测试路径、选择器或 shell 命令。

   如果找不到能证明某个 Task 的测试，Task 会进入 needs_generation：
   专门的测试生成阶段先补充测试、重新收集选择器并做基线执行，再把测试
   绑定到 Task。没有绑定就不会进入普通实现流程。

3. 机器证据是唯一完成门槛

   每次验证都会保存命令、退出码、选择器、收集数量和输出摘要。只有
   exit_code 为 0 的证据，才能把 Task 标记为通过。验证失败会回到当前
   Task 继续修复，不会悄悄跳到下一个任务。

4. Todo 和 Task 分层

   Todo 是模型执行过程中的临时步骤，例如“阅读模块”“修改接口”“运行
   局部测试”。Task 是用户可验收的交付单元。Todo 完成不会改变 Task 的
   验证状态，避免把“做了很多事”误判成“交付正确”。

5. 依赖、暂停和恢复都是持久化的

   Goal、Task、验证状态和错误信息会落盘。复杂任务可以暂停、恢复、取消，
   不依赖模型临时记忆。旧的混合状态不会被静默兼容，而会明确提示不支持，
   避免恢复到不可靠的执行模型。

6. 双重检查，而不是双重裁决

   可选 evaluator 会查看验收标准、代码差异和验证证据，发现范围偏离或
   测试覆盖不足。它是建议者，不能把失败或缺失的机器验证改判为通过。


执行流程
========

  Goal
    -> Planner: 生成 Task、验收标准和依赖
    -> Test Catalog: 只接受仓库中真实可收集的 pytest selector
    -> PREPARE_TESTS: 没有测试时先生成、收集和绑定测试
    -> ACT: 一次只实现一个 Task
    -> VERIFY: 执行该 Task 的绑定测试，保存证据
    -> EVALUATE: 可选的独立代码审查
    -> COMPLETE: 通过后完成 Task，解锁依赖任务
    -> FULL VERIFY: 全部 Task 完成后运行整个 Goal 的回归命令


与普通循环式 Agent 的区别
=========================

普通的循环式 Agent 往往以“下一轮继续尝试”为中心。ProofTask 以“下一步
是否有足够证据”为中心。

  普通循环                         ProofTask
  ------------------------------  -----------------------------------
  模型自己描述进度                  每个 Task 有持久化状态和验收条件
  测试命令可由模型临时猜测          selector 必须来自系统测试目录
  Todo 完成容易被视为任务完成       Todo 不影响 Task 完成状态
  一次失败可能混入后续工作          失败固定回到当前 Task
  计划和执行容易脱节                Task、测试绑定和证据绑定在同一记录
  恢复时依赖上下文和提示词          Goal/Task 图和状态落盘恢复

这也是 ProofTask 相比 LoopX 一类自主循环框架重点补上的部分：循环能力很
重要，但对工程交付而言，可靠的“完成判定”和“测试归属”更重要。


适合谁
======

- 想让 Agent 持续处理复杂改造，但不接受“它说改好了”
- 需要把一个需求拆成有依赖的多个交付任务
- 希望测试文件、测试选择器和具体 Task 有明确对应关系
- 需要可暂停、可恢复、可审计的自主执行过程
- 正在给团队或开源项目引入 AI 编码工作流


快速开始
========

安装依赖：

  pip install -r requirements.txt

启动命令行：

  python main.py

启动一个 Goal：

  /goal --verify "python -m pytest -q" -- 修复分页接口并补齐边界测试

查看或控制运行：

  /goal status
  /goal pause
  /goal resume
  /goal cancel

其中 --verify 是所有 Task 完成后的全局回归命令；每个 Task 自己执行的是
由 Test Catalog 绑定的聚焦测试。


可靠性承诺
==========

- 不接受模型编造的测试路径或 selector
- 不允许无证据的 Task 完成
- 不让 evaluator 覆盖机器测试结果
- 不让未完成依赖的 Task 提前开始
- 不静默迁移旧的混合 Goal 状态
- 通过权限控制、超时、暂停、取消和错误记录限制失控执行

项目定位
========

ProofTask 不是另一个只会延长上下文的 Agent Loop。

它是一个把“目标 -> 任务 -> 测试 -> 证据 -> 交付”连成闭环的自主编码执行器。
当任务变复杂时，重点不再是让模型多跑几轮，而是让每一次推进都值得相信。
